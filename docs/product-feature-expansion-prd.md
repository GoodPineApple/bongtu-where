## 0. Executive summary

**한 줄:** 사용자는 “어디에 봉투가 있는지”만이 아니라 “**지금 살 수 있는지**”를 알고 싶다. 공공데이터는 **정적이고 재고를 말해주지 않으므로**, 지도 위에 **익명 제보·최신화·공유**를 얹은 제품이 시장에서 차별화된다.

**제안 요약:** (1) 재고 제보의 **서버 반영·출처 표시**, (2) **딥링크·공유**로 바이럴 루프, (3) 지도 외 **보조 피드(커뮤니티/공지)** 탭, (4) **법적·신뢰 레이어**(개인정보처리방침, 데이터 기준일), (5) 탐색 **필터 확장**(영업·지역)을 우선순위화한다.

---

## 1. Context & problem

### 1.1 시장 맥락

- 종량제 봉투 수급 이슈로 **실구매 가능 여부**에 대한 수요가 있다.
- 공공데이터는 **판매점 목록·좌표**에는 강하지만 **실시간 재고**에는 약하다.

### 1.2 우리 서비스의 현재 상태 (요약)

- 지도 중심 UI, 공공 JSON 기반 판매소 로드, 검색·규격 필터, 바텀시트 상세, **재고 제보는 클라이언트 시뮬레이션**에 가깝다.
- Supabase·적재 파이프라인은 **데이터 백엔드로 확장 가능**한 기반이 있다.

### 1.3 핵심 문제 정의

| 문제 | 사용자 영향 |
| :--- | :--- |
| 재고 정보가 **개인 브라우저에만** 남음 | 다른 사람·다른 기기와 **진실이 공유되지 않음** |
| 특정 매장을 **URL로 열 수 없음** | 카톡·커뮤니티로 **전파가 어려움** |
| 지도만 있으면 **맥락·논의**가 부족 | “이 동네 품절” 같은 **집단 지성**이 쌓이지 않음 |
| 데이터 **기준일·제보 정책**이 불명확 | 신뢰·법적 리스크 |

## 2. Product thesis

> **“공공데이터로 ‘어디’를, 군중 제보로 ‘지금’을 보여준다.”**

- **정적 레이어:** 공공 판매소 (신뢰 가능한 골격).
- **동적 레이어:** 익명·경량 제보로 재고 상태 갱신 (차별화).
- **성장 레이어:** 공유 URL·피드로 **재방문 이유**를 만든다.

---

## 3. Goals & non-goals

### 3.1 Goals (6–12개월 관점)

1. 사용자가 **특정 판매소의 최근 재고 상태**를 서비스에서 신뢰하고 행동(방문·전화)으로 이어가게 한다.
2. **공유 1회당 재방문** 비율을 높인다 (딥링크).
3. 법·신뢰 최소선을 갖춘다 (개인정보, 데이터 출처).

### 3.2 Non-goals (이번 문서 범위에서 의도적으로 제외)

- 전국 **재고량 실측**·POS 연동 수준의 정밀 재고 관리.
- 소셜 로그인·프로필 기반 **신원 강제** (초기에는 익명·경량이 가설상 유리할 수 있음).
- 배달·결제 등 **거래 클로즈** 기능.

## 6. Solution principles (구현 시 지켜야 할 원칙)

1. **한 손 조작:** 제보는 1~2탭 안에서 끝낸다.
2. **출처 분리:** 공공 필드 vs 사용자 제보 필드를 UI에서 구분한다.
3. **악용 가정:** 익명 제보는 **속도 vs 신뢰** 트레이드오프를 명시하고, P2에서 품질 신호를 도입한다.
4. **성능:** 마커 수가 많을 때를 전제로 **뷰포트·클러스터** 등은 엔지니어링 백로그와 연동한다 (본 PRD의 기능 범위는 “무엇을 제공할지”에 집중).

## 9. Risks & mitigations

| 리스크 | 완화 |
| :--- | :--- |
| 익명 제보 남용 | 속도 제한, 시간 감쇠, (후속) 신고·블라인드 |
| 공공데이터와 불일치 | **공공 스냅샷 기준일** 고정 표기 |
| 법적 이슈 | 개인정보처리방침, 위치 권한 설명, 제보 데이터 최소 수집 |

## 10. Open questions (결정 필요)

1. 제보는 **로그인 없이** 갈지, **경량 디바이스 ID**만 쓸지.
2. 재고 상태 외에 **텍스트 코멘트**(예: “20L만”)를 P1에 넣을지.
3. 공공데이터 갱신은 **수동 임포트**로 충분한지, 주기 자동화가 필요한지.
